# Database setup and upgrade

PostgreSQL schema is generated from the actual JPA models by `SchemaExportTest`. `code/src/main/resources/schema.sql` creates a fresh schema and foreign keys; `data.sql` adds only reference interests. No accounts or test conversations are seeded. Spring SQL auto-initialization is disabled. Docker PostgreSQL runs these files only when its data volume is empty.

For an existing database, take a database backup and run **only** `code/src/main/resources/db/upgrade-final.sql` using the deployment account, then deploy with `JPA_DDL_AUTO=validate`. Never run the fresh schema script over the shared database, and do not delete the Docker volume to upgrade. The upgrade adds `chat_rooms.deleted_at`, the shared-key biography table, indexes, and copies existing biographies. `users.bio` remains a compatibility column: reads fall back to it for old accounts without a profile row; profile edits update both columns so old snapshots can still read biographies during rollout. No existing records are dropped.

The One-to-One is User ↔ UserProfile, with user_id as both PK and FK; cascade ALL/orphanRemoval belongs to the user lifecycle and the small biography object is eagerly loaded to keep detached profile DTO conversion safe. Room → RoomMember is explicit One-to-Many, LAZY, with no cascading deletion. Other links are LAZY Many-to-One. UserInterest/RoomInterest are composite-key join entities; gallery is an ordered element collection, maximum five photos enforced in the API. Messages, rooms and account moderation retain records rather than cascade-delete histories. SQL foreign keys use restrictive deletion.

See `diagrams/er.mmd` and `data-dictionary.md` for the complete schema. Indexes cover active memberships, unread notifications, pending friend requests, room discovery and message history. Unique email/name/compound primary keys come from generated DDL. Existing duplicate social relationships are not silently deleted by this upgrade.

Direct room creation obtains a transaction-scoped lock on a canonical participant row before selecting/restoring/creating the conversation. Both callers select the same UUID regardless of who opens first. Existing duplicate direct rooms from older versions are retained; reads deterministically select the oldest active room rather than failing with a non-unique query result. This upgrade never merges/deletes legacy messages automatically. If older duplicates contain different histories, export and reconcile them separately after backup.
